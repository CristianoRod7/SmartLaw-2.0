[1] 프로젝트 한줄 개요
SmartLaw-2.0는 계약서 분석을 중심으로, AI 상담/문서 작성, 법률 뉴스 조회, 그리고 스마트팜 시뮬레이션 확장 축까지 포함하는 법률·리스크 진단 플랫폼으로 발전 중인 프로젝트입니다.
이번 커밋(fix: remove nested repo) 이후 구조는 기존 app/api/v1/*.py 단일 라우터 파일에서 app/api/v1/endpoints/*로 재배치되어, API 계층 정리가 진행된 상태입니다.
프론트엔드는 기존 pages 중심 구조에서 modules/core_analyze, modules/smartfarm_simulator, shared로 확장되어 기능 단위 모듈화가 시작되었습니다.
핵심 기능은 “업로드 → 분석 → 리포트/대시보드”의 end-to-end 흐름이며, 스마트팜 도메인 설정(SmartfarmConfig, SmartFarmFields, Simulator)이 별도 축으로 분리된 점이 이번 구조 변화의 핵심입니다.

[3] 최상위 폴더별 역할 설명
app/: 백엔드 핵심. API 엔드포인트, 서비스, DB 모델/세션, AI 프롬프트를 담당.

frontend/src/: 사용자 UI 및 인터랙션. 이번엔 modules/ 도입으로 기능 단위 구조가 강화됨.

app/prompts/: 도메인별 프롬프트 자산 분리. 향후 산업별 확장의 핵심 기반.

app/services/: OCR, AI, 크롤링 등 비즈니스/외부 연계 로직 집약.

frontend/src/modules/: core 분석 엔진 + 스마트팜 시뮬레이터 모듈을 분리한 구조(팀 협업 유리).

루트 .gitignore/.env: 운영/보안에 직접 영향. 이번 커밋에서 변경됨.

삭제 흐름 포인트: app/api/v1/analyze.py 등 구형 위치 파일 삭제 시작 → endpoints/ 중심으로 수렴 중.

[4] 하위 폴더 및 파일 상세 분석
아래는 중요도 순으로 기술.
(추정) 표시는 파일명/경로 기반 분석.

app/main.py
역할: FastAPI 앱 생성 및 v1 엔드포인트 연결 허브.

위치: 백엔드 진입점.

연결 모듈: app/api/v1/endpoints/*로 재배선되었을 가능성 높음(추정).

실행 흐름: 모든 HTTP 요청의 최초 진입.

중요 이유: 아키텍처 실제 활성 경로를 결정.

개선 포인트: 라우터 import를 중앙 router registry로 분리하면 유지보수 향상.

app/api/v1/endpoints/analyze.py
역할: 계약 분석 API.

요청: 파일 업로드(계약서), 분석 이력 조회(추정).

연결: document_service.py + ai_service.py + DB 모델.

반환: 분석 점수/리스크 섹션/요약(JSON) 구조(기존 패턴 추정).

중요 위치: 핵심 수익 기능(분석)의 실질 API 관문.

app/api/v1/endpoints/chat.py
역할: 상담/서류 작성 챗봇 API.

요청: 문서 유형 + 사용자 메시지 + 히스토리.

연결: ai_service.py의 chat 생성 로직.

중요 위치: 계약 분석 이후 행동유도(문서 작성) 시나리오 핵심.

app/api/v1/endpoints/legal.py
역할: 정책/법률 뉴스 조회 API.

요청 흐름: 프론트 호출 → 외부 뉴스/정책 소스 조회 → 가공 반환(추정).

중요 위치: 서비스 지속 방문을 유도하는 정보 허브.

app/core/config.py
역할: 환경설정 로딩.

중요성: DB 키, AI API 키, 외부 API 키의 단일 관리점.

개선: dev/stage/prod 분리 및 필수값 검증 강제 필요.

app/db/session.py
역할: DB 연결 세션 수명주기 관리.

중요성: API 안정성/트랜잭션 신뢰성 핵심.

개선: pooling/timeout/retry 정책 정교화 권장.

초기 설치비, 대출 여부/규모/금리, 월 고정비/변동비, 인력 수, 예상 연매출

정책 정보

손해 가능성은 “운영지표”만으로 안 되고, “계약 조항 + 정책 의무 + 비용 구조”가 결합되어야 정확하게 진단 가능하기 때문.
